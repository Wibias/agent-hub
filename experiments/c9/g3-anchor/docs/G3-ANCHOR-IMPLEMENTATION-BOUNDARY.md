# G3 Anchor v0.1 | security decision and failure matrix

This review candidate implements the narrow Anchor-facing half of `G3-EXTERNAL-WITNESS-CONTRACT-V1.md` on the existing G3 branch. There is no merge, provisioning or release authorization.

| Situation | Required result |
| --- | --- |
| Signed fresh independent audit head equals local journal | Sign short-lived scoped `/v1/current` response |
| Audit unavailable, invalid pin/nonce, stale time, different revision/hash | No signed head, HTTP 503 |
| Non-owner invokes `/v1/advance` | HTTP 403 before mutation |
| Valid owner but CAS mismatch or forged root manifest | No state change |
| External audit CAS is declined, times out, or response invalid | DENY/UNKNOWN; the in-process uncertain latch stays set |
| Audit CAS commits but local append fails | DENY/UNKNOWN; old local journal is not signed, manual forward recovery required |
| Local journal append committed and audit head rechecked successfully | Report COMMITTED for this review protocol |
| Torn/corrupt local journal or unexpected restart | Refuse startup or further reads; no automatic truncation or rollback |
| Revoked key reintroduced under the same ID or SPKI | DENY (journal check; independent audit must enforce an immutable tombstone history too) |
| Old local journal restored with a newer valid audit head | DENY until separately authorized forward recovery |

The local file append plus `Flush(true)` does not prove whole-system atomicity or power-loss durability. The CAS operation is only as trustworthy as the separately administered audit backend. The server trusts a backend receipt when its signature and scope match; this does **not** independently prove its claimed WORM durability. The code intentionally exposes no public endpoint for forward recovery, epoch reset, or first enrollment. Remote `GetCurrent` and `AdvanceHead` API implementation, durable audit anchoring, protected journal path ACL/owner validation and independent operations remain HOLD.

All private signing keys stay in externally provisioned Windows certificate store in the review server; no keys are generated by application code. The acceptance tests generate disposable keys only in memory. Real issuer/root provisioning and out-of-host independence have **not** occurred. Even a successful source build does not grant permission to deploy or perform writes.
