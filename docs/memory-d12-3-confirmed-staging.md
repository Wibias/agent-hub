# D12.3: Confirmed atomic rule staging (Phase 3, opt-in only)

Related: Issue #186, stacked Draft PR #187 (shadow), Draft PR #188
(provenance and local rule draft).

**No production writes and no automatic project-Memory creation in this PR.**
This implementation is an isolated, explicit API for future reviewed use.

## Confirmation and authority model

The chat user explicitly approved a *permanent* project QA rule. That is
a valid decision in the ChatGPT conversation, but not evidence automatically
available to the separate Windows Agent Hub SQLite database. Do not forge
this missing source or infer an authenticated Agent Hub event from the chat.

The future authenticated Codex user-prompt hook must capture a NEW direct-user
confirmation message, with the **exact proposed single-rule text**, project,
branch and local draft reference, and must correctly classify its authority.

Required text is generated by atomicRuleConfirmationText(). Format:

    MEMORY CONFIRM PERMANENT PROJECT RULE DRAFT_REF FOR REPO@BRANCH: FULL_RULE_TEXT

Required confirmation Evidence: original user-prompt source of kind session
with codex harness, non-empty session ID, matching project/branch, normal
sensitivity and user_direct authority. Required already-stored metadata:

- event_type = user_prompt
- explicit_memory = true
- explicit_memory_mode = atomic_rule_confirm
- atomic_rule_draft_ref = exact DRAFT_REF

The current Codex hook does **not** yet record atomic_rule_confirm metadata.
Therefore actual production staging is **not enabled**. Do not fabricate
metadata via manually inserted records, and do not treat a CLI argument or
assistant paraphrase as a user confirmation.

## Stage only, not canonical Claim

memory-engine/memory-atomic-confirmed-staging.mjs supplies:

- installAtomicRuleStagingSchema(db): explicit standalone schema install,
  never called on MemoryEngine startup, hook execution, or import
- atomicRuleConfirmationText(args): future exact user-authority prompt format
- stageConfirmedAtomicRule(args): transaction that validates source Candidate,
  original Evidence, scope, atomic review spans, draft reference and new
  authenticated direct-user confirmation Evidence

The sidecar stores **no canonical rule text**. It stores a rule SHA-256 and
references to existing source and confirmation Evidence. A second table
stores exactly selected source spans by stable review reference plus offsets
and SHA-256.

One BEGIN IMMEDIATE transaction ensures staging row and all provenance rows
commit together or roll back entirely. Unique confirmation-evidence and
source/rule constraints prevent duplicate replay. Equivalent retries are
reported as already_staged.

The result reports durableClaimCreated=false, promotionAllowed=false and
originalCandidateModified=false. The original mixed Candidate never changes
status. No Claims, claim_evidence, lifecycle or Recall state is modified.

## Test-only evaluation on disposable databases

    node --test tests/memory-engine/memory-atomic-confirmed-staging.test.mjs

Tests use the actual MemoryEngine schema and synthetic Evidence in temporary
SQLite databases. They cover scope, authority, source integrity, draft and
source offsets, exact confirmation text, freshness, duplicate replays,
schema opt-in, atomic rollback, foreign keys, no production Claim writes.

**Do not run the staging API on a real user database yet.**

## Future production prerequisites

1. Add a separate explicit direct-user hook parser, with real user-prompt
   evidence capture and bounded source authentication; no simulation or
   fake credentials in production.
2. Design and independently review promotion from the sidecar into a canonical
   Claim using a **single atomic transaction** with source and confirmation
   Evidence linkage; do not bypass MemoryEngine authorization and lifecycle.
3. Verify conflict/same/update handling, approval and revocation,
   canonical export/import, backup/restore, retention, deduplication,
   search indexing, Git branch isolation, and concurrent worker races.
4. Test opt-in rollout only on disposable WAL-safe backup copies; require
   explicit operator review before any production DB migration.
5. Avoid reusing the legacy whole-Candidate confirm flow. That could
   preserve one-off tasks from a mixed prompt.

The permanent user decision has been made; **persistent Agent Hub Memory is
not created until these security and migration gates pass.**
