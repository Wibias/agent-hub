## Critical scope correction

P19 proves the *Quick* runtime's operational health and exact record/pattern parity with legacy. It does **not** prove that a repository-default retrieval mode has been implemented or is safe to enable for all queries.

At P25:

- `readP17ActivationState()` returns `repository_default_graph_enabled: false` for both graph and legacy state; P17 has no repo-default writable control.
- The P17 projection sets only `REFERENCE_GRAPH_QUICK_RUNTIME=graph`.
- P11 authorizes Graph only for `profile=quick`, and only with exact parity. Standard and Deep remain `legacy-control`.
- Even on a successful Quick graph route, P11 deliberately returns the legacy-selected public records and patterns. The soak is not evidence of improved relevance.
- The P19 evaluator expressly rejects any sample where `repository_default_graph_enabled !== false`. It **cannot** be reused unchanged as the acceptance gate after a future repo-default change.

Therefore **do not patch a local JSON flag, environment variable, scheduler task, CLI, or database policy to force default-on**. There is no authorized repo-default promotion procedure yet.

## Architecture audit: why a simple default-on toggle is incorrect

The production query implementation currently executes
`const profile = args.profile || "standard"` in
`knowledge/design-references/scripts/query.mjs`.
The design-with-ai adapter and knowledge index document explicit
`--profile <profile>` invocations. P11 only supports Graph for
`profile=quick`; Standard and Deep are deliberately zero-network legacy.

Consequences:

- Treating "repository default" as "replace missing --profile with quick"
  would silently change selection size, coverage quotas and the user's implied
  `standard` contract. It would also miss the documented explicit-profile
  callers. **This is not an equivalent or useful repository-wide rollout.**
- Treating "repository default" as "graph for every profile" would exceed
  the proved Quick-only P10/P11 projection, parity requirements and
  P19 readiness evidence. Standard/Deep cannot be enabled without their own
  transport, parity and outcome-quality verification.
- Quick's current graph handoff deliberately returns the legacy public
  selection/pattern payload after exact parity; a successful route does
  not establish a changed or improved recommendation.

**Recommended next design boundary:** preserve the existing profile and output
contracts while designing *explicitly scoped* graph support for Standard and
Deep separately. Introduce a versioned, default-off policy only after its
target request surfaces and authority are specified; do not reuse P17 Quick
state as a broad activation switch. Implement a separate post-change
monitoring receipt because P19's default-off invariant cannot certify a
default-on rollout.

Any future release proposal must spell out: explicit and omitted profile
behavior; controlled callsites; output and coverage invariants; on/off
authority; failure fallback; health/latency/quality gates; rollback owner
and procedure. Until these are settled and reviewed, **no live default
routing change is proposed**.

## Phase B: design, implement and review a separate default route

Before proposing any mutable promotion:

1. Define **exactly which requests** are covered by “repository default”, and how explicit profile choices override it. Preserve Standard/Deep legacy until separately validated and authorized.
2. Implement an independently controlled **default-off**, versioned, fail-closed control plane with one deterministic source of truth, explicit change ID and complete audit receipt.
3. Design a true rollback that restores pre-change behavior without consuming/reusing the existing P18/P16 one-shot grant. Abort if rollback cannot be proven with independent before/after probes.
4. Enforce existing production project binding and publishable-only runtime reads. No new public attestation or direct P16 ledger permissions.
5. Define bounded runtime overhead, latency budgets, real-user safety/quality metrics and error-rate thresholds. The P25 Quick soak covers none of these end-user decision metrics.
6. Cover malformed state, stale authority, concurrent changes, network/HTTP/timeout, graph parity mismatch, listener failures, clock gaps and failed rollback with deterministic tests.
7. Add a **new** post-change monitoring receipt and guard. Do not stretch P19's default-off invariant to count post-promotion traffic as healthy.
8. Require exact implementation SHA, green CI, independent code/security review, explicit approval that names scope and revision, operator dry-run, and a predeclared rollback trigger before any mutation.
