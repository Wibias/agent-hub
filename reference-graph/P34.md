# P34: independent Standard/Deep pattern and public-output parity (OFFLINE)

**Status: independent implementation / local test evidence only. NO-GO for production Standard/Deep Graph, default-on, migration or merge without review.**

Stack: P27 #226 -> P28 #227 -> P29 #228 -> P30 #229 -> P31 #230 -> P32 #231 -> P33 #232 -> **P34 #233**.

## Gap closed

P27 preserves ordered record/pattern identity fingerprints for 48 Standard/Deep cases. P29 and P33 compare the selected **record** IDs and coverage gaps, but do not recreate actual pattern decisions or the complete public output. A perfect P33 record-order report therefore cannot certify public-equivalence of patterns, scored records, requested fields or coverage structures.

P34 adds `reference-graph/p34-pattern-public-output-parity.mjs` as a separate **offline read-only** comparator. It never imports or calls the legacy `selectRecords` or `selectPatterns`, the P11 production query/router, the Supabase client, a usage recorder or a filesystem writer.

## Inputs and trust requirements

The comparator receives:
- an already verified P30 candidate DTO pool, whose candidate identity-set SHA-256 and count must match a separate, structurally valid, pinned P33 audit report;
- frozen P27 Standard/Deep baseline JSON (48 ordered-record and pattern ID hashes);
- the 24 unchanged source templates;
- the canonical local record catalog (without filesystem-private `__file` fields);
- the canonical local pattern catalog (without `__file`);
- a separately archived baseline of 48 SHA-256 fingerprints of the **complete P11 legacy-control public JSON outputs**.

All six JSON inputs require individually provided SHA-256 hashes. The verifier checks exact bytes against those supplied digests before comparing. It rejects incomplete baseline coverage, malformed/duplicate IDs, invalid P33 flags, malformed P28 candidates or identity mismatches. Private source records, patterns, and other raw inputs never appear in the report.

**Independent provenance is not created by self-hashing these inputs.** The operator must collect the control snapshots and their digests from a separately pinned, approved legacy-control revision, not from the proposed P34 output. CI tests deliberately generate their own fixture pins for repeatable regression only.

## Two independent comparisons

1. **Pattern parity:** Starting from the P29-selected candidate IDs, P34 hydrates only the matching pinned local records and independently scores frozen reviewed patterns. It uses the selected example/counterexample links, request tokens, lexical overlap, deterministic tie-break and Standard/Deep pattern limits. It does not invoke the legacy pattern selector. The resulting ordered pattern ID hash and count must match the separately pinned P27 reference.
2. **Complete public-output parity:** P34 independently reconstructs record `selectionScore`, diversity penalties, stratum/coverage values and gaps, requested fields, redacted record data, scored patterns and the precise P11 public JSON field order. Each full JSON result's SHA-256 must match the frozen legacy-control output fingerprint for the same case.

This catches changes that record or pattern identity hashes cannot catch, e.g. altered pattern explanatory text or record content when the selected IDs are unchanged.

The aggregate report returns `record_order_exact_cases`, `pattern_exact_cases`, `public_output_exact_cases`, combined mismatch counts, and explicit `pattern_parity_verified` / `public_output_parity_verified` limited to the **supplied offline candidate set and baseline**.

**Always false:** `live_graph_parity_verified`, `deployment_authorized`, `eligible_for_activation`, `repository_default_graph_enabled` and `activation_performed`.

## Read-only legacy baseline export

On an independently reviewed and pinned legacy-control checkout, with a clean working tree, export the control output hashes for a precise reference date:

```powershell
node reference-graph/cli/p34-freeze-legacy-public-baseline.mjs --date 2026-11-07 > p34-legacy-public-baseline.json
if ($LASTEXITCODE -ne 0) { throw 'P34 legacy public baseline failed' }
Get-FileHash -Algorithm SHA256 .\p34-legacy-public-baseline.json
```

The CLI performs 48 explicit `graphMode: 'legacy'` P11 read-only requests with usage recording disabled and emits only case keys and output SHA-256 digests. It does not save a file itself, make a Graph/Supabase request, change production routing or start a collector. **The example date is historical; future live evaluation must use the separately approved current reference date and corresponding refreshed source receipt.** Capture the exact output bytes/hash through an independent approved archive process; the local `Get-FileHash` alone is not a deployment authority.

## Validation limits

- P34 tests use the real local catalog and a simulated P30 response already processed by P33. A green 48/48 result therefore demonstrates **offline implementation equivalence only**, not current live Graph candidate parity, query quality, network behavior or authorized release readiness.
- The comparison covers the 24 fixed request templates under the Standard and Deep defaults, not every possible query, limit, date or catalog state.
- P34 cannot independently attest that the supplied remote candidate content is fresh or authentic beyond the P33 source count/hash and the chosen output cases; the P31 ID-set hash does not fingerprint all candidate metadata.
- Common normalization primitives (`tokenize`, `overlap`, `stripInternal`) are shared with the legacy implementation. The pattern ranking and public-output reconstruction are separate implementations, but shared primitives are a residual common-mode risk. A frozen external baseline is required.
- Patterns/public outputs remain sourced from an **offline pinned local catalog**. This does not enable remote Graph to replace local reference hydration or authorize a new output source.
