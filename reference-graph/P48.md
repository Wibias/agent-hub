# P48: authenticated loopback-only P47 coordinator (NO-GO for production)

**Default-off, isolated lab-only.** P47 persists signed revocation state; P48 reads that state on each authenticated GET via a server bound strictly to `127.0.0.1`. There is no HTTP mutation route.

`startP48AuthenticatedLabCoordinator` requires a random base64url bearer token (at least 32 random bytes) supplied by the test operator, plus a P47 signed-state reader. Requests with missing, duplicate or wrong authorization headers fail. Non-GET methods, unknown paths and body-bearing GETs cannot access state. Errors produce generic status responses without leaking keys, paths or candidate data. Each successful request re-reads P47 to enforce durable revocations and reject incomplete journals. No permits are cached.

The coordinator holds **no private Ed25519 signing key** and cannot issue authorizations. P46 workers separately validate the signed envelope, dedicated project/commit/lab identity, lease expiry and sequence. The bearer token is a separate *read-only lab credential*, not the owner signing key.

Tests should use ephemeral Ed25519 keys and random bearer tokens. Exercise real independent Node worker processes, invalid bearer requests, credential rotation, coordinator restart, persisted revocation and partition failures. The test-only server is never started by production routing.

**Security boundary:** This is **HTTP over loopback, not TLS/mTLS**. Never proxy or expose its port to other hosts. A real multi-host service requires verified TLS/mTLS, authenticated independent signer trust, a durable backend with fenced lease/revocation transactions, protected nonce/sequence ledger, operational metrics and rollback rehearsal. Local host administrators can tamper with test files or environment. Successful P48 tests do not constitute production readiness.

P11, public query, historic P33/P35, Supabase and Windows monitoring are untouched. Activation remains NO-GO in issue #275.

## Separate operator process (localhost lab only)

The P48 coordinator can now be started **in its own Node process** using `reference-graph/cli/p48-run-lab-coordinator.mjs`. It reads an explicit private local JSON manifest with the P47 store directory, public Ed25519 verification key file, SHA256 pin, repository SHA and lab identity. It accepts only `mode: isolated-shadow-rehearsal`, `default_off: true`, `production_route_wiring: false` and Standard/Deep profiles. All paths must be absolute; files must be real (not symlinks) and bounded in size.

The read-only worker token is supplied **only** through the local environment variable `P48_LAB_READ_TOKEN`, not the CLI arguments or manifest. The process never reads a private Ed25519 signer key. It preflights the durable P47 signed state before opening its loopback HTTP listener, prints only its localhost endpoint and non-authorizing flags, and closes on SIGINT or SIGTERM.

Example manifest schema (not a credential or deployable production config):

```json
{
  "schema_version": "reference-graph.p48-lab-operator-config.v1",
  "scope": { "mode": "isolated-shadow-rehearsal", "profiles": ["standard","deep"], "default_off": true, "production_route_wiring": false },
  "directory": "/private/p48-lab-state",
  "public_key_path": "/private/p48-lab-test-public.pem",
  "public_key_sha256": "<64 lowercase hexadecimal digest>",
  "repository_sha": "<exact 40-char repository SHA>",
  "lab_id": "isolated-lab-only-identifier"
}
```

**No signing key, worker secret, service-role credential or P11 activation value belongs in this manifest.** The example is illustrative; placeholders deliberately cannot pass the validator. A restarted worker still separately verifies every signed P46 response. No persistence grant may be inferred from successful daemon startup.

Only loopback HTTP is supported, not external host access. To proceed to an actual multi-host release, this must be replaced by an independently governed TLS/mTLS deployment with authenticated durable signer, lease issuance/revocation, fence and operator rollback rehearsal. P48 is not that deployment.
