# P62: version-scoped release review record and approval policy

**Status: NONEXECUTING CONTRACT ONLY. Code merge is not Graph activation.**
This is the written successor to P35's historical PR-stack lock for future
Standard/Deep Graph *activation reviews*. The old P35 lock is intentionally
unchanged and cannot authorize a new release.

## What exists and what does not

The P40 Ed25519 preflight validates a signed scope syntactically, but does
not verify that a key is independently trusted, that a signer is the owner,
that a nonce is fresh across production hosts, or that rollback works.
The new P62 pure function accepts a separate, strictly shaped review record
and validates requested project, commit, profiles, evidence references,
reviewer/owner separation, duration and revocation plan. It cannot verify
the referenced bytes, signatures, authority or real operational controls.
Even with a perfectly shaped record, its decision is always
activation_authorized=false, repository_default_graph_enabled=false.

No new release actuator, production routing import, database/cron write,
service secret, monitoring task, key store, signing service, or deployment
is created.

## Mandatory immutable release-review record

Schema version: reference-graph.p62-release-review-record.v1
Evaluation module: reference-graph/p62-release-review-preflight.mjs

Every future requested review must include:

- Exact repository Wibias/agent-hub and the *then-current deployed main SHA*;
  the SHA must match independently verified current GitHub and production
  deployment identities. Never silently reuse the 2026-11-09 #274/#276/#277
  code-merge waiver or the older P35 lock.
- Project vrznfnxzlxaavpqbzbzd, separate operator ID and trusted host,
  repository owner ID Wibias, and a distinct qualified independent human
  reviewer, who is not the operator or owner. These ID strings are not
  independently authenticated by the P62 function.
- Exact profile allowlist: standard and/or deep. Quick is outside scope.
  One canary percent from 1 to 5, default_off=true, a strictly UTC window
  no longer than 60 minutes, current UTC snapshot date and an exact UTC
  refreshed-at timestamp no older than four hours.
- External SHA256 references for the seven source/evidence commitments:
  original P26 frozen source; new independent P7/P31 source witness;
  48-case same-snapshot Standard/Deep records, patterns and full public JSON;
  sustained service-only protected Data API monitoring over 24 hours;
  production multi-host fencing; production rollback rehearsal; and
  post-change monitoring.
- Two separate SHA256 commitments to the independently reviewed human
  attestation and the owner's explicit *activation* decision. A digest
  alone does NOT prove the contents are valid, signed or approved.
- A unique release nonce, externally controlled revocation ledger anchor,
  rollback-plan SHA256, and the full fail-closed trigger set:
  manual revoke, invalid signature, expired evidence, stale source,
  HTTP error, timeout, parity mismatch, quality regression, latency budget,
  critical monitor and rollback drill.

## Required approval chain BEFORE any runtime actuator can be considered

1. An authorized operator collects read-only evidence at an approved host.
   Independently authenticate source system, project, record chronology,
   UTC timestamps and original external digest archive. The lost 2026-11-08
   P31 receipt is not recreated or retroactively accepted.
2. A distinct qualified independent reviewer examines the exact bytes,
   source provenance, same-snapshot parity, positive AND negative protected
   Data API probes, complete window metrics, trust store and rollback
   rehearsal. Reviewer signs an immutable decision that is independently
   verifiable under a trusted separately administered key.
3. Only after this review, the repository owner must provide a **new,
   explicit, release-specific production activation approval** with exact
   main SHA, project, profiles, canary percent, trusted operator, time window,
   fail-closed criteria, rollback and revocation. A chat instruction to merge
   code is explicitly *not* this approval.
4. Before every attempt, a future independently reviewed production
   controller must verify both human signatures against preprovisioned
   independent trust anchors; verify the underlying evidence bytes and
   sources; atomically consume the single-use nonce across all hosts;
   check revocation and an active monitor; and perform the scoped cutover
   with strict automatic Legacy fallback. None of these operations
   exists in P62.
5. A dry-run or rollback failure, stale witness, missing two-hour window,
   loss of trusted monitor/coordinator, or source/content mismatch means
   **NO-GO**, with Legacy kept authoritative and Quick unchanged.
   Production rehearsal and fresh post-change checks are separately
   required before any release is approved.

## How to interpret P62 tests

The synthetic test includes hashes shaped like valid release approvals,
and deliberately returns contract_valid=true while every trusted authority
and release flag remains false. This proves syntactic shape, NOT approval.
Any invalid project, commit, identity separation, unknown profile, time
window, missing digest or rollback trigger fails the structural check.

The P62 preflight is intentionally never imported by P11, the public query
CLI, or an activation path. This contract by itself is NOT completion of
#275's governance gate: a trusted identity/revocation system and actual
owner-signed approval are still missing.

The live release status remains **NO-GO** under issue #275.
