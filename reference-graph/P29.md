# P29: independent offline Standard/Deep selection parity

Status: **OFFLINE PARITY ONLY / NO LIVE GRAPH ROUTING / NO DEFAULT ACTIVATION**  
Prerequisites: P27 legacy baseline (#226), P28 candidate metadata contract (#227).  
This PR (#228) stacks on the P28 branch, which stacks on the P27 branch.

## Contract

The P29 candidate selector only reads the P28 candidate metadata. It does
not use the legacy `selectRecords` function, hydrate source records, invoke
the P10 Graph transport, or rely on any production activation state.

The implementation independently reproduces these legacy selection
behaviors for Standard and Deep: request size validation, scoring of
surface/platform/lexical and evidence features, visual-verified bonus,
text-only penalty, diversity penalties, deterministic tie-breaking and
Deep's per-stratum minima/maxima.

The *comparison harness* independently creates the P27 legacy baseline
using the unchanged legacy selector, then compares the P29 ordered
candidate legacy-ID fingerprint and coverage gaps. Only the aggregate
comparison is exported; individual record and candidate IDs remain local.

The expected reference date is supplied separately, and must exactly
match the P27 baseline date. No implicit system time is accepted.

## Read-only CLI

From the separately pinned development checkout:

```powershell
node reference-graph/cli/p29-offline-profile-parity.mjs --date 2026-11-07
if ($LASTEXITCODE -ne 0) { throw 'P29 offline parity failed or diverged' }
```

A `0` exit code means no order or coverage mismatches in the inspected
offline set. A `2` means a comparison mismatch. A `1` means invalid
inputs or local read failure. The CLI does not write data or make network
requests.

The canonical fixture has 24 design-reference request scenarios run through
both Standard (12 record default) and Deep (28 record default), for a total
of **48 offline profile cases**.

## Scope of the evidence

Even complete offline agreement with P27 cannot establish:

- P10/P28 live Graph transport or Supabase projection correctness
- Graph runtime freshness, RLS, latency and error behavior
- Independent pattern selection or public output parity
- Improvement in relevance or visual evidence quality
- Repository-default authority, rollback, or post-change monitoring
- Any authorization to deploy or merge without separate independent review

The P27/P28/P29 data all originate from the local legacy catalog. A
true end-to-end Graph runtime comparison still requires a separately
versioned publishable projection, verified schema/policy/freshness and
independent output and pattern parity proof. Do not call a local
identity match `live_graph_parity_verified`.

## Safety

writes, Task Scheduler changes, usage log writes or routing overrides.
Keep the existing P25 Quick collector pinned and operational.
