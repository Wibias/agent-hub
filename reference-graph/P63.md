# P63: audit all 12 protected Data API windows (offline, no release)

**Status: default-off evidence quality improvement, not a production soak.**

P59/P60 showed four HTTP 200 responses from the service-only protected
candidate view, all inside a few seconds of one two-hour window. A separate
pair of HTTP 401 responses came from expected anonymous/publishable negative
authorization tests. Those 401s must never be counted as positive protected
server evidence. There is still no observed complete 24-hour service-only soak.

P63 exposes a tiny offline-only coverage reconciler:
- reference-graph/p63-protected-http-coverage.mjs
- reference-graph/cli/p63-audit-protected-coverage.mjs
- tests/reference-graph/p63-protected-http-coverage.test.mjs

It requires an explicit, completed 24-hour UTC window aligned to two-hour
boundaries, synthesizes all **12 two-hour slots even if HTTP logs omit a slot**,
and compares aggregate protected HTTP 200 counts against optional successful
P61 reports. A missing log row means zero observed successful requests, NOT
unknown-but-passing. P61 reports are not necessarily independently signed,
and existing P61 CLI output reports only successes. The evaluator therefore
never treats its own operator-supplied inputs as proof of a complete,
independently observed attempt journal or source provenance.

The output always contains these fields set to false:
- edge_logs_independently_authenticated
- complete_attempt_journal_verified
- p61_source_provenance_independently_attested
- sustained_privileged_data_api_soak_verified
- activation_authorized
- repository_default_graph_enabled

Even operator_claimed_full_window_coverage=true would be a structural
observation only, not signoff or activation authority.

## Reproducible read-only operator procedure

1. Choose exactly 12 completed consecutive even-UTC two-hour windows and
   record the start/end timestamps, e.g. the completed interval from
   2026-11-08T22:00:00.000Z up to but excluding 2026-11-09T22:00:00.000Z.
2. Use the Supabase read-only unified edge-logs query against dedicated
   project vrznfnxzlxaavpqbzbzd with that exact UTC start/end window:

~~~sql
SELECT toStartOfInterval(timestamp, INTERVAL 2 HOUR) AS window_utc,
       countIf(log_attributes['response.status_code'] = '200') AS http_200,
       countIf(log_attributes['response.status_code'] != '200') AS http_non_200,
       count() AS attempts
FROM logs
WHERE source = 'edge_logs'
  AND position(log_attributes['request.path'],
      'reference_graph_profile_candidates_server_p30_v1') > 0
GROUP BY window_utc
ORDER BY window_utc
~~~

   Pass the exact requested time range to the Supabase logs API. It may
   return only windows with requests. Normalize each returned window to a
   strict YYYY-MM-DDTHH:mm:ss.000Z UTC string. Do not invent missing rows.
   This query observes aggregate endpoint traffic, not the authentication
   context, quality of returned candidates or end-to-end client latency.
3. If present, separately archive the exact P61 success reports, their
   independently authenticated source/host identity and hashes. Do not
   synthesize P61 reports from generic HTTP 200 status codes. In particular,
   P61 currently has no independently verified failed-attempt audit journal;
   this remains a blocking evidence requirement.
4. Create a private, sanitized operator input JSON outside Git with this
   schema (illustrative incomplete historical input, NOT acceptance):

~~~json
{
  "schema_version": "reference-graph.p63-operator-coverage-input.v1",
  "window_start_utc": "2026-11-08T22:00:00.000Z",
  "window_end_utc": "2026-11-09T22:00:00.000Z",
  "edge_windows": [
    {
      "window_utc": "2026-11-09T18:00:00.000Z",
      "http_200": 4,
      "http_non_200": 0,
      "attempts": 4
    }
  ],
  "operator_observations": []
}
~~~

   Two separate HTTP 401 responses observed at 2026-11-09 22:46 UTC are
   outside this 24-hour sample and must not be added to it.

5. Run on a trusted checkout using Node 24 or newer:

~~~powershell
node .\reference-graph\cli\p63-audit-protected-coverage.mjs --input C:\audit\reference-graph\p63-input.json
if ($LASTEXITCODE -ne 0) { throw 'P63 audit BLOCKED' }
~~~

   The summary contains only aggregate counts and UTC window names. A
   reporter can archive the original local input and hash separately, but
   merely hashing on the same machine is not independent source attestation.

## Remaining release requirements

Even 12/12 structural positive windows do not establish a trusted soak.
A trustworthy release gate additionally requires a full independently
authenticated all-attempt journal (including failed P61 calls), source
witness provenance, valid positive service-only authorization, cross-window
timestamp/refresh correspondence, actual client-side latency/error budgets,
quality parity and independent source/signature verification.

P63 never registers a cron/scheduled job, calls Supabase, reads a key,
changes production P11/P30 routing, or authorizes a canary/rollback.
Issue #275 remains the only release tracker: **Graph activation NO-GO.**
