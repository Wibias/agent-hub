# P39: P31 access hardening and P38 monitoring

Status: **P39 migration 016 installed in the dedicated Supabase project;
five-minute monitoring prepared but not activated; no routing activation**. P31
and P38 are installed. This PR does not re-apply 014, 015, or 016.

## Data requirement

P33/P34/P37 need the complete P30 candidate DTO for exact parity and content
binding. That is all 19 P31 columns: the 16 P28 candidate fields plus
`projection_version`, `snapshot_date`, and `refreshed_at`. Public roles do not
need source text, editorial tags, provenance/topology, internal IDs, or product
metadata to monitor freshness.

## Access model

Migration 016 revokes direct table access from `public`, `anon`, `authenticated`
and `service_role`.

- `public.reference_graph_profile_candidates_server_p30_v1` exposes the full
  19-column current-UTC snapshot to `service_role` only. It is
  `security_barrier`, filters to the current UTC date, and is the required
  relation for the server-side P30/P33/P34/P37 audit path.
- `public.reference_graph_profile_public_p30_v1` exposes only
  `projection_version`, `snapshot_date`, and `refreshed_at` for the read-only
  P38 freshness probe. It deliberately exposes no `product`, `search_text`,
  `tags`, `asset_id`, `legacy_id`, `public_id`, `source_family`, or `topology`.
  There is no other proven public consumer; any broader public view requires a
  separate classification and migration.
- The P31 base table remains RLS-enabled as defense in depth. Its refresh
  function remains `SECURITY DEFINER`, owned by the migration role, and
  executable only by `service_role`.

The live catalog has 181 distinct `product` values. Product is therefore
**INTERNAL** until a separate PUBLIC classification is approved; it is absent
from the public view. The earlier `public_id = SHA256(legacy_id)` design is
rejected: an unsalted deterministic hash is pseudonymous, not anonymous, and
is vulnerable to dictionary/correlation attacks against known or guessable
legacy IDs. No public identifier is exposed in 016. Any future public ID must
use a randomized opaque identifier or an approved non-public mapping, and that
decision must be documented separately.

P30 keeps its publishable mode for the historical base-relation contract, but
after this migration that mode fails closed because the base table is no longer
public. Existing full-candidate clients must use the explicit server mode:

```js
fetchP30ProfileCandidateSnapshot({
  accessMode: 'server',
  serviceKey: process.env.SUPABASE_SECRET_KEY,
  // ...same trusted pins...
});
```

P33 and P37 forward `serviceKey`/`accessMode` to P30. The service credential
must stay in the server process/environment; it is never logged or placed in
the URL. The public freshness view is the only direct browser/anon surface.

The existing P32 anon PostgREST smoke is a historical pre-P39 surface check;
the P39 CI step runs after it and applies 016. New public clients have no
general candidate surface; full-candidate clients must use server mode. Do not
point the P32 historical smoke at a P39-hardened database and treat its failure
as a product regression.

## Security-invoker view review

Both P39 views use `security_invoker = true` plus `security_barrier = true`.
They therefore execute with the caller's privileges and RLS rather than the
view owner's, avoiding the Supabase `security_definer_view` ERROR class
entirely.

The least-privilege boundary is:

- `anon`/`authenticated` hold column-level SELECT only on
  `projection_version`, `snapshot_date`, and `refreshed_at`. The public view
  selects exactly those columns; direct reads of those three columns are
  equivalent exposure and remain subject to the current-UTC RLS policy. No
  sensitive column is granted.
- `service_role` holds full base-table SELECT and, in Supabase, has
  `BYPASSRLS=true`. No service-role RLS policy is created: it would be inert
  in that runtime and would falsely imply containment. Direct service-role
  base reads can see current **and historical** rows by design; this is a
  trusted privileged boundary, and the service credential never reaches a
  browser or public client. The server **view** is the supported transport:
  its explicit current-UTC `WHERE` returns only the current snapshot even
  though the same service role can see historical base rows directly.
- The base table remains RLS-enabled. The server view is `service_role` only;
  the public view is `anon`/`authenticated` only and exposes no product, source
  text, tags, internal IDs, or derived public ID.
- Both views explicitly filter `snapshot_date = current UTC date`. The
  service role's direct base access is broader by design; only the server
  process holds that credential. The P39 smoke sets the disposable service
  role to `BYPASSRLS=true` to mirror Supabase, asserts that direct base reads
  see the stale fixture row, and asserts that the server view excludes it.
  This role change is confined to the P39 smoke/fixture and does not modify
  the role used by earlier CI tests.

Before application, run Supabase Security Advisor. The expected result is **no
security-definer view ERROR** and no unexpected public table/column grant. A
column-level grant on the three freshness fields is intentional and must be
listed in the pre/post receipt. Any ERROR, unexpected `anon`/`authenticated`
access to a sensitive column, or missing RLS policy blocks rollout. A future
broader public surface requires a new `security_invoker` view with explicit
column grants and classification; it must not fall back to owner-rights views.

## Rollback

This rollback deliberately restores the previously exposed public base-table
read. Use it only as an explicitly authorized break-glass action, never as an
automatic response to an alert.

```sql
begin;
revoke all on public.reference_graph_profile_public_p30_v1
  from public, anon, authenticated, service_role;
revoke all on public.reference_graph_profile_candidates_server_p30_v1
  from public, anon, authenticated, service_role;
drop view if exists public.reference_graph_profile_public_p30_v1;
drop view if exists public.reference_graph_profile_candidates_server_p30_v1;
revoke all on table public.reference_graph_profile_runtime_projection_p30_v1
  from anon, authenticated, service_role;
grant select on public.reference_graph_profile_runtime_projection_p30_v1
  to anon, authenticated;
commit;
```

Rollback does not touch the P38 cron job, P10 Quick projection, P11 routing, or
the P31 refresh function. Verify the target and obtain approval before running
the `grant select` step.

## P38 monitoring and alerting

The monitor is read-only and is not scheduled by this phase. It evaluates a
snapshot produced by a read-only health query and emits a deterministic alert
plan. The snapshot contract is
`reference-graph.p39-p38-health.v2`; it includes a dedicated cycle history:

```json
"cycles": {
  "consecutive_failed": 0,
  "last_cycle_start": "2026-11-08T00:00:00.000Z",
  "last_cycle_status": "succeeded"
}
```

- A **cycle** is one even UTC hour and its 0/5-minute invocations. A failed
  cycle has no successful invocation. One failed cycle is WARN; two or more
  consecutive failed cycles is CRITICAL via `consecutive_failed`.
- Auto-resolve requires two independent healthy observations whose
  `observed_at` timestamps are at least five minutes apart. A single healthy
  snapshot never resolves an alert. The CLI persists the next state with
  `--state-out` so a scheduler cannot resolve from in-memory-only data.
- WARN: refresh age over 2h15m, one failed cycle/run, no success in 2h15m, or
  p95 over 1500 ms. CRITICAL: job missing/inactive, two failed cycles, empty or
  count/hash-mismatched projection, wrong UTC date after 00:10, refresh age
  over 4h, API-visible count zero while the projection is non-empty, or a
  401/403. No automatic refresh or remediation is performed.
- A **24-hour soak is 12 two-hour cycles** (each cycle has two invocations),
  not four cycles. `evaluateP38Soak` requires 12 cycles, at least a 24-hour
  span, no gap over 2h15m, two invocations per cycle, and at least one success
  per cycle. All cycles must be healthy before any Standard/Deep activation
  request.

The evaluator is `reference-graph/p39-p38-monitor.mjs`; the CLI is
`reference-graph/cli/p39-p38-monitor.mjs`. Both are fixture-testable and do not
connect to production unless an operator supplies a snapshot. The read-only
cycle producer is `reference-graph/p39-p38-health-snapshot.sql`; it derives
`consecutive_failed`, `last_cycle_start`, and `last_cycle_status` from
`cron.job_run_details` and must run only under an authorized monitor role.

## Prepared production monitoring boundary

The full P38 monitor remains **BLOCKED** for a five-minute production loop
because the trusted local environment has no read-only database credential or
aggregate health RPC for cron/job/source data. The existing local Task
Scheduler tasks and their publishable-key config are trusted, but they do not
provide that privileged read-only path.

A separate **public freshness monitor** is prepared for a five-minute local
schedule. It uses only the existing publishable-key config and the three-column
public freshness view. It verifies exact count, current UTC date, Content-Range
total, refresh age, mixed refresh instants and API latency. Its reports
explicitly carry `source_hash_verified=false` and `cron_history_verified=false`;
it must not be represented as the full P38/cron/source monitor.

Monitor` is registered and enabled on a five-minute schedule, and it runs only
the public freshness probe. It predates this change; this PR neither registers

existing P10/P19 tasks are not modified. Atomic state,
