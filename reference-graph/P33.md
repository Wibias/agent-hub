# P33: independently pinned Standard/Deep record-selection parity via P30 transport

**Status:** REVIEW-ONLY. No live Reference Graph access, deployment, pattern parity, authorization or routing changes.

Stack: P27 #226 -> P28 #227 -> P29 #228 -> P30 #229 -> P31 #230 -> P32 #231 -> P33 #232.

## Why

P29 demonstrated 48/48 record-order and coverage comparisons over an **offline, local** candidate projection. P32 demonstrated a real PostgREST roundtrip over only five synthetic candidates. Neither connects the complete received P30 candidate set to an independently frozen P27 baseline. P33 closes that comparison-harness gap without touching the production router.

## Independent bytes and target binding

`reference-graph/p33-pinned-profile-parity.mjs` exports `auditP33PinnedProfileParity`.

A caller supplies these unmodified JSON strings and **independently obtained SHA-256 hashes**:
- the frozen P27 baseline (24 scenarios x Standard/Deep = 48 cases);
- the unchanged 24-case request template file;
- the operator-only P31 source-side receipt, with P7 count, canonical legacy-ID-set SHA-256 and UTC snapshot/refresh binding.

The evaluator checks exact raw bytes against all three pins before making an HTTP call. It refuses missing or altered pins, malformed/extra receipt fields, stale or wrong-day receipts, unbounded source counts and incorrect project identity. The project is pinned to the committed `reference-graph/target.json` identity `vrznfnxzlxaavpqbzbzd` and its exact HTTPS URL.

**Trust boundary:** `candidate_content_sha256` is a binding of the response P33 actually saw, **not** an independently authoritative content digest from the P31 source. P31 remains an independently pinned source-side count/ID-set receipt; it does not currently certify every candidate metadata value. A forged operator-supplied P33 report with a self-computed hash does not prove a live read.

**Trust boundary:** a digest computed from the same untrusted artifact is not independent verification. The caller must obtain the approved baseline/template/receipt digest through a separate trusted process and preserve provenance. P33 cannot authenticate an operator's authority merely from matching user-supplied hashes.

P30 is invoked for a **GET-only**, publishable-key read. It rejects malformed metadata, stale/mixed snapshots, incorrect source count and ID-set hash. P33 additionally requires the returned snapshot refresh instant to match the independently pinned receipt exactly.

## Comparison and output

After successful source/transport validation, P33 passes the actual returned candidate DTOs to the independent P29 Standard/Deep selector. It compares the 48 cases with P27 for:
- exact ordered record ID fingerprints;
- record counts;
- coverage gap kinds.

The **versioned P33 v2** aggregate report (schema `reference-graph.p33-pinned-profile-parity.v2`) includes `exact_order_cases`, `mismatch_cases`, per-profile mismatch counts, candidate count and legacy-ID-set hash, `candidate_content_sha256` and the `record_order_coverage_parity_exact` status. The new candidate content fingerprint hashes **all 16 candidate DTO fields including tags and search text**, canonically sorted by `asset_id`, independent of JSON object property order. It contains no plaintext candidate data and binds the exact P30 snapshot seen by P33 to a subsequent P34 audit. Old v1 P33 reports cannot satisfy the strengthened P34 v2 input gate. It does not return individual reference IDs, search text, raw P27 cases, URLs, keys or operator receipt contents.

**Always false:** `pattern_parity_verified`, `live_graph_parity_verified`, `repository_default_graph_enabled`, `activation_performed`, `deployment_authorized`, `eligible_for_activation`.

Even a perfect 48/48 test is **not a deployment permission or full output parity**. P27's expected pattern fingerprints cannot be verified from candidate-only results; independent pattern/public-output parity must be implemented and proved separately.

This proves composition and negative contracts; it is explicitly *not* independent production evidence or a live Supabase test. Do not treat the test-generated baseline/hash as trusted operator material.

The connected Supabase integration cannot access the dedicated AgentHub Reference Graph project. Do not deploy migration 014 into any other project. Do not store credentials or production candidate content in GitHub.
