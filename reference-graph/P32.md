# P32: disposable PostgREST integration and complete P28 publication gate

**Status: REVIEW-ONLY; isolated PostgreSQL/PostgREST CI only. No live Supabase target, no production migration, no routing or collector mutation.**

Stack: #226 P27 -> #227 P28 -> #228 P29 -> #229 P30 -> #230 P31 -> #231 P32.

## Why P32 exists

P31 ensures source IDs, their `primary_stratum`, and publication count/hash are consistent with P7. A further contract hole existed: older P7 test rows may have `surface_family='auth'`, while P28 permits only twelve taxonomy values such as `auth-onboarding`. P31's previous refresh could publish structurally valid Graph rows that the P30/P28 runtime client must reject.

P32 adds fail-closed checks **before** the projection is replaced: `surface_family`, `platform`, `access_status`, `evidence_class`, searchable text and tags must meet the P28 metadata vocabulary, as must the existing primary stratum. A failure leaves the previous published snapshot untouched. This is additive to P31's already tested count/hash and transactional rollback behavior.

Only the disposable CI legacy fixture data are normalized to conform to the same taxonomy. No local or production design-reference catalog is rewritten or reclassified.

## Ephemeral PostgREST

The P32 CI adds an official pinned `postgrest/postgrest:v16.4` service on a runner-local port, connected only to its disposable test PostgreSQL. It does NOT contact any Supabase project.

The test establishes that:
- The P31 service-only aggregate source receipt is produced by PostgreSQL independently of the public HTTP response and pinned before P30 reads.
- PostgREST GET returns the published rows through `anon` SELECT and RLS, with actual PostgreSQL timestamptz encoding.
- The standalone P30 selector transport validates the real HTTP response for count, identity-set SHA-256, version, UTC binding, P28 candidate DTO, and non-activation flags.
- A wrong count or identity fingerprint fails closed.
- Anonymous POST/PATCH/DELETE and calls to the privileged P31 refresh are denied over PostgREST.
- A same-date snapshot with refresh timestamp five hours old is rejected as `snapshot-stale`.
- A prior-date snapshot stays physically present but returns zero public rows due to RLS; P30 rejects the empty result.
- P10/P11 runtime code and the P25 Quick/Windows collector remain unchanged.

**Scope limitation:** A test-only `fetchImpl` forwards the P30 client's checked HTTPS URL to local plain-HTTP PostgREST. This exercises the real DB -> REST -> DTO path, *not* TLS, Supabase's API gateway/key validation, project-specific RLS configuration, any production connection, or live candidate parity.

The PostgREST fixture is small and synthetic; it cannot establish the 48-case Standard/Deep match against P27. This phase does not verify pattern/output parity, quotas with the full current catalog, quality, latency or actual release readiness.

## Deployment gates still closed

The connected Supabase integration does not expose the dedicated reference-graph project. No attempt to deploy to another connected project is allowed.

Before any live data read or deployment: independent review/approval of the exact P31/P32 migration, verified target identity and authority, current schema/grants/RLS audit, trusted operator-side source receipt, full candidate set, separate live parity and pattern/output comparisons, latency budget, default-off activation authority and rollback rehearsal.
