# Reference Graph P19 — Production Soak and Promotion Readiness

P19 observes the already activated Quick Reference Graph runtime and proves that the real P18 activation has exactly one durable P16 consumption row. It does **not** promote the repository-default graph and does not consume another activation grant.

## Hard boundary

P19 is read-only with respect to production activation state:

- no P17 apply or rollback;
- no P16 nonce consumption;
- no activation grant generation or signing;
- no repository-default graph enablement;
- no public or anonymous ledger inspection.

The only elevated operation is a one-time aggregate attestation RPC after migration 011 is deployed. Ongoing production samples use the publishable runtime transport only.

## 1. Governance before live deployment

Migration 011 (`reference-graph/schema/011_reference_graph_activation_attestation.sql`) may be deployed to the dedicated production project only **after the exact P19 implementation SHA has passed repository governance and the implementation has been merged according to the normal release process**.

The dedicated target remains:

```text
project ref: vrznfnxzlxaavpqbzbzd
URL:         https://vrznfnxzlxaavpqbzbzd.supabase.co
```

Migration 011 adds only:

```text
public.reference_graph_attest_activation_consumption_p19(text,text,text)
```

The RPC is `SECURITY DEFINER`, read-only, and executable only by `service_role`. It returns only `matching_count`, `total_count`, and `exact_match`. It does not expose nonce, consumption ID, timestamp, grant, signature, or key material, and it does not grant direct SELECT on the private P16 ledger.

Because the currently connected Supabase MCP identity does not have migration/SQL permission on this project, do not weaken database privileges to work around that limitation. Use an explicitly authorized production operator/migration path after governance is green.

## 2. One-time P18 consumption attestation

From the AgentHub runtime root (`%USERPROFILE%\.agents` on the production Windows host), load the exact target and an elevated Supabase key into the **current PowerShell process only**:

```powershell
$env:SUPABASE_URL = "https://vrznfnxzlxaavpqbzbzd.supabase.co"
$env:SUPABASE_SECRET_KEY = "<current sb_secret_... key>"
```

A legacy `SUPABASE_SERVICE_ROLE_KEY` is supported only as the existing fallback when no modern secret key is available.

Choose an external state directory and run the attestation once:

```powershell
$P19Dir = Join-Path $env:LOCALAPPDATA "agent-hub\reference-graph"
New-Item -ItemType Directory -Force $P19Dir | Out-Null

node reference-graph/cli/p19-production-soak.mjs `
  --attest-consumption `
  (Join-Path $P19Dir "p19-attestation.json")
```

Expected healthy result:

```json
{
  "matching_count": 1,
  "total_count": 1,
  "exact_match": true,
  "healthy": true,
  "blockers": []
}
```

The complete receipt also binds the exact frozen P18 evidence SHA-256, production project ref, authority SHA-256, request hash, and grant payload hash. It never includes the P16 nonce or consumption ID.

Immediately remove elevated credentials from the operator shell:

```powershell
Remove-Item Env:SUPABASE_SECRET_KEY -ErrorAction SilentlyContinue
Remove-Item Env:SUPABASE_SERVICE_ROLE_KEY -ErrorAction SilentlyContinue
```

The P18 grant used for the real activation is already consumed. **Never reuse that consumed grant.** Any future mutating ceremony must use a newly signed grant under that ceremony's own authorization contract.

## 3. Configure publishable-only production sampling

Hourly soak samples need only the production URL and current publishable runtime key:

```powershell
$env:SUPABASE_URL = "https://vrznfnxzlxaavpqbzbzd.supabase.co"
$env:SUPABASE_PUBLISHABLE_KEY = "<current sb_publishable_... key>"
```

Do not set an elevated key for scheduled sampling. Even if an operator process happens to contain one, the P19 core strips `SUPABASE_SECRET_KEY` and `SUPABASE_SERVICE_ROLE_KEY` before calling the P17 production probe.

Recommended sample file:

```powershell
$P19Dir = Join-Path $env:LOCALAPPDATA "agent-hub\reference-graph"
$P19Samples = Join-Path $P19Dir "p19-soak.jsonl"
```

Run one sample:

```powershell
node reference-graph/cli/p19-production-soak.mjs --sample $P19Samples
```

A healthy sample requires all of these simultaneously:

- production source is `reference-graph`;
- Quick graph is enabled;
- repository-default graph remains disabled;
- Quick routes to `reference-graph`;
- Quick record parity is exact;
- Quick pattern parity is exact;
- Standard remains `legacy-control`;
- Deep remains `legacy-control`.

An unhealthy sample is still appended to the JSONL evidence, then the CLI exits nonzero. Probe exception details are not persisted; the durable blocker is only `probe-error`.

## 4. Run the soak hourly

Run `--sample` **every hour**. P19 does not install a scheduler automatically; use the host's existing scheduler/operator mechanism.

The readiness gate requires:

- at least 24 samples;
- every sample healthy;
- first-to-last sample span of at least **24 hours**;
- no adjacent sample gap greater than 90 minutes;
- repository-default graph disabled in every sample.

Because 24 samples exactly one hour apart span only 23 hours, a normal hourly run should collect **25 samples from hour 0 through hour 24** before expecting readiness.

Do not edit away an unhealthy sample or a long gap. The JSONL history is operational evidence, not a success-only log.

## 5. Evaluate promotion readiness offline

After the soak window, evaluate the one-time attestation and accumulated JSONL without elevated credentials:

```powershell
$P19Dir = Join-Path $env:LOCALAPPDATA "agent-hub\reference-graph"

node reference-graph/cli/p19-production-soak.mjs `
  --evaluate `
  (Join-Path $P19Dir "p19-attestation.json") `
  (Join-Path $P19Dir "p19-soak.jsonl") `
  (Join-Path $P19Dir "p19-promotion-readiness.json")
```

A clean result has:

```json
{
  "eligible": true,
  "required_window_hours": 24,
  "required_samples": 24,
  "allowed_max_gap_minutes": 90,
  "attestation_exact": true,
  "blockers": []
}
```

`eligible=true` is **readiness evidence, not permission to promote**. P19 never changes repository-default routing. A later default-promotion phase must define and receive its own explicit authorization before any mutation occurs.

## 6. Failure handling

P19 is fail-closed:

- wrong Supabase target → no probe;
- missing publishable key → no probe;
- P17 state drift → unhealthy sample;
- Quick parity failure → unhealthy sample;
- Standard/Deep routing drift → unhealthy sample;
- probe exception → `probe-error`;
- P16 attestation mismatch → readiness blocked;
- malformed JSON/JSONL → evaluation fails;
- duplicate sample timestamps → readiness blocked;
- gap greater than 90 minutes → readiness blocked;
- less than 24 hours → readiness blocked;
- repository-default graph observed enabled → readiness blocked.

None of these failures authorizes a mutation or a retry of the consumed P18 grant.

## Current phase status

Until migration 011 is deployed and the one-time production attestation succeeds, P19 repository implementation alone provides no new live ledger evidence. Until the full soak window evaluates `eligible=true`, no default-promotion readiness claim should be made.
