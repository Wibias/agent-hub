# P64: private local P61 attempt journal (default-off)

**Status: code-only operator preparation, not deployed, NOT an approved 24h soak.**

P61 exposes positive, sanitized HTTP observations but the original one-shot
command emits no durable record when a request fails, times out, or the
process terminates unexpectedly. P63 explicitly requires a trusted,
independently authenticated all-attempt journal before a 24-hour
protected Data API soak can be considered. P64 supplies only the **local
capture mechanism**, not that trusted independent evidence.

## What P64 adds

- reference-graph/p64-attempt-journal.mjs
- reference-graph/cli/p64-journal-protected-attempt.mjs
- tests/reference-graph/p64-attempt-journal.test.mjs

A human/operator must explicitly invoke P64 once per observation.
P64 delegates the GET to the unmodified P61 operator CLI. No privileged
HTTP request happens until a NEW private attempt directory has been created
and its start.json written and fsynced. Every completed call writes a separate
finish.json with outcome passed or blocked. Only a valid successful
P61 report gets a third file, p61-success.json, with its exact content
SHA256 pinned in finish.json. No exception text or HTTP error response body
is ever recorded.

If execution is interrupted between start.json and finish.json, the offline
inspector reports incomplete. It never treats a missing terminal file,
stale witness, failed output write or unverified report bytes as a successful
probe. All file creation is exclusive and fails if the attempt directory
already exists. Local files are created with mode 0600 under an operator
provided private parent directory; Windows/NTFS ACLs must be verified
separately by the host administrator.

## Trusted host (one explicit invocation)

Use a clean verified checkout of main and a pre-existing, private parent
directory OUTSIDE the repository. The operator must obtain a fresh P40
source-versus-P31 witness from a separately authenticated read-only DB
connection and independently archive the exact witness bytes/digest. The
project secret must be injected locally into P40_SUPABASE_SECRET_KEY
using an approved trusted secret manager. Never paste that credential
in chat, GitHub, a third-party browser, logs or CLI arguments.

PowerShell 7 example, with the hash deliberately a placeholder:

~~~powershell
$witness = 'C:\audit\reference-graph\p40-witness.json'
$pin = '<independently-archived-current-witness-sha256>'
$attempt = 'C:\audit\reference-graph\attempt-20261110-0000-01'

node .\reference-graph\cli\p64-journal-protected-attempt.mjs --witness-file $witness --witness-sha256 $pin --attempt-dir $attempt
if ($LASTEXITCODE -ne 0) { Write-Warning 'P64 attempt blocked or incomplete' }

# Offline inspection works with no Supabase credential.
node .\reference-graph\cli\p64-journal-protected-attempt.mjs --inspect-dir $attempt
Get-ChildItem $attempt | Get-FileHash -Algorithm SHA256
~~~

The first P64 invocation must run before the witness expires, on an
authorized server with a protected sb_secret_ credential. The inspect command
makes no network call and requires no key. The journal path must not exist
before the first invocation. Do not overwrite or repair missing files.

## Limitations and the evidence review boundary

- P64 is NOT an automatic 24h scheduler. It neither starts a recurring
  process nor registers a Supabase cron job or Windows Task Scheduler task.
- A local start/finish pair is not independent proof that every intended
  two-hour sample occurred. Missing invocations require a separate,
  independently approved full-window schedule and trusted off-host attempt
  inventory to detect. Local fsync improves persistence but does not by
  itself prove power-loss durability, independently trusted timestamps, or
  tamper resistance across machines.
- P61's generic fail-closed rejection hides exact failure causes. P64 records
  blocked status, not an invented HTTP status or a claimed timeout reason.
  Actual gateway HTTP status/error logs and client telemetry must be
  collected independently to prove the requested SLO.
- The P64 local inspector detects malformed/missing/tampered journal files
  but does NOT authenticate their origin, complete request count, external
  signature or independently pinned provenance.
- The existing P63 coverage evaluator still requires independently
  authenticated complete gateway aggregates and optional P61 successes;
  P64 does not modify P63 or claim that requirement is met.
- P11 Quick and Legacy routing, P30 transport, P40 trust rules, production
  databases, scheduler/cron, keys, deployments and release flags unchanged.

Both P64 and P63 hardcode NO-GO release decisions. The seven separate
activation prerequisites in GitHub issue #275 remain open. An actual trusted
server run and an independently signed complete full-window archive are
mandatory before considering the protected API operational gate.
